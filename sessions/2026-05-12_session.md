### 2. Stronger password rules everywhere

Three new constraints layered on top of the existing 8-char / upper / lower / number / special rule:

- **Cannot reuse old password** on reset → `BCrypt.Verify(newPass, oldHash)` from `db.GetPasswordHash(email)`.
- **Cannot contain username** → static helper `ContainsIdentity(password, params tokens)` does a case-insensitive substring check, ignoring tokens < 3 chars (so a short first name doesn't block every password).
- **Cannot contain real name** → same helper, passes `profile.FirstName` and `profile.LastName`.

Applied in three places (matching the existing pattern of duplicating per-window):
- `MainWindow.xaml.cs` → `FinalReset_Click` (reset flow) + `RegisterStep3_Click` (signup, after username is chosen).
- `ProfileWindow.xaml.cs` → `SavePassword_Click` (in-profile change-password).

Identity-check helper exists once per file (`ContainsIdentity` is a `private static` method in both `MainWindow.xaml.cs` and `ProfileWindow.xaml.cs`).

### 4. 15-minute reset-token expiry (in-memory)

The reset email promised "valid for 15 minutes" but nothing enforced it. Now enforced.

**Approach** (chosen because user said "don't over-complicate"): a `private static Dictionary<string, DateTime> _resetTokenIssuedAt` in `MainWindow.xaml.cs`, plus `TimeSpan ResetTokenLifetime = TimeSpan.FromMinutes(15)`.

- `SendReset_Click` records `DateTime.UtcNow` for the email after a successful send.
- `VerifyCode_Click` checks `DateTime.UtcNow - issuedAt > 15 min` → "This code has expired. Please request a new one."
- Code is single-use: dict entry is removed on successful verify.

**Caveat we accepted**: the dict is in process memory only. If the app is restarted between request and verify, the code is treated as expired. Fine for the academic scope. If we ever want persistence, add a `ResetTokenIssuedAt` column to the `user` table.

### 5. Profile embedded inside Dashboard (was a separate window)

Big one. Previously `NavProfile_Click` opened `new ProfileWindow(CurrentUser).ShowDialog()`. Now the profile lives inside the Dashboard window — same nav bar stays at top, content area swaps.

**Refactor**
- `ProfileWindow.xaml` → still named that file-wise (to keep the diff small), but the class is now `ProfileView : UserControl`:
  - Root element `<Window>` → `<UserControl>`, `Window.Resources` → `UserControl.Resources`.
  - Stripped `Title`, `Width`, `Height`, `WindowStartupLocation`.
  - **Deleted the second top bar** (the small Financy logo + "← Back to Dashboard" link). The Dashboard's existing top nav bar serves that role now.
  - Adjusted `Grid.RowDefinitions` from 3 rows (top bar / content / footer) to 2 rows (content / footer).
  - Removed `Back_Click` handler from `ProfileWindow.xaml.cs`.
- `Dashboard.xaml` — wrapped the existing `ScrollViewer` in a new `Grid x:Name="MainContentHost"` and added a sibling `ContentControl x:Name="ProfileHost" Visibility="Collapsed"`.
- `Dashboard.xaml.cs`:
  - `NavProfile_Click` builds a fresh `new ProfileView(CurrentUser)`, sets it as `ProfileHost.Content`, hides `DashboardContent`, shows `ProfileHost`.
  - New `ShowDashboardView()` helper tears the profile down (`Content = null`, field cleared) and calls `RefreshDashboardAvatar()` in case the avatar was changed.
  - All other nav buttons (`Transactions`, `Budget`, `Goals`, `Reports`, `Groups`) now call `ShowDashboardView()` before their MessageBox so clicking them while inside the profile cleanly leaves it.

**Files renamed conceptually but kept on disk**: `ProfileWindow.xaml` and `ProfileWindow.xaml.cs` still hold the `ProfileView` class. Did this to minimize csproj churn. Safe — .NET doesn't require filename to match class.
